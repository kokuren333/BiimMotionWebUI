## 1. 目的と非目的

### 1.1 目的

1. **解説動画の制作ハーネスを MV と同じ水準に引き上げる。** MV 制作で確立した「設計が先」「方向性の複数案」「スタイル定義が先」「演出目的つきストーリーボード」「ゲート」「失敗チェックリスト」「入力支援」を、解説動画の性質（理解させることが目的、根拠が要る、音声を自前で合成する、キャラが演じる）に読み替えて、ジョブ内指示・検証スクリプト・WebUI・スペース版仕様に入れる。
2. **WebUI の見た目から汎用AI生成テンプレート感を除き、この道具固有のデザイン言語に置き換える。** 機能は一切落とさない。
3. **repo を渡されたエージェントが、階層ワークフロー（PM → オーケストレーター → 実働 → 下請け）と制作哲学に自動で従うようにする。** repo ルートに自走ハーネスを置き、分業できない環境での縮退運転も定める。
4. **この改良作業そのものを上記ワークフローで行い、初回の実証とする。**

### 1.2 非目的（今回やらないこと）

## 2. 解説動画ハーネス強化の要件

### 2.1 MV の知見：移植するもの／しないもの

**移植する（読み替えて入れる）**

| MV の知見 | 解説での読み替え | 理由 |
| --- | --- | --- |
| 思想先的設計（何を表現するかが先、手段は後） | **理解先的設計**（何を理解させるかが先、見せ方は後）→ 2.2 | 現行の解説指示は演出の規則から始まり、目的の固定が無い |
| 楽曲構造 → 映像構造の翻訳 | **説明構造 → 映像構造の翻訳** → 2.3 | 「静的スライドにしない」とあるだけで、どう動きに変えるかの方法が無い |
| 視覚的密度と変化率の区別 | **認知負荷と変化率の区別**（一度に出す新規概念の数と、画面変化の速さは別軸） | 解説の失敗は情報の詰め込みで起きる |
| 強調と抑制 | **理解の山場**を1〜2箇所決め、演出の頂点をそこへ一致させる | 既定デザイン文は視聴維持を強く求めるので、頂点の置き場所を規定する必要がある |
| 方向性3案＋多様性軸＋差別化メモ＋`plan/direction.md` | 軸を解説用に再定義して導入 → 2.4 | 解説は方向性を1案も比較せずに実装へ進んでいる |
| スタイル定義を先に、キャラシート、`plan/style-sheet.md` | **図解様式の定義**（線・色の意味・強調色の用法・文字階層）と**演者の演技語彙**を先に決める | 図解の様式が場面ごとにばらつく。GLB キャラは外見が固定なので、決めるべきは演技の語彙 |
| ストーリーボードの演出目的欄 | 場面ごとの**説明目的・構造型・画面状態の遷移**欄 → 2.5 | 現行は項目の列挙のみで様式が無い |
| 検証ループ（音と通し視聴、still、時刻・問題・期待する改善） | そのまま。加えて**構造検証／正確性検証／理解評価**の3つを区別 | 解説には「正しいか」という第三の観点がある |
| レンダーゴースト再発防止（レイヤー分離、preview/final 走査、孤立と連続の分類、二重レンダー） | **両モード共通の章へ昇格**し、解説工程に組み込む | 字幕は発話ごとに差し替わるテキストで、ゴーストの典型的な発生源。F4 の不一致も解消する |
| 歌詞レイヤー QC ゲート（事前合格で制作へ、事後合格で完了） | **台本・根拠・字幕の QC ゲート** → 2.6 | 解説で取り返しがつかないのは誤情報と読めない字幕 |
| 失敗パターンのチェックリスト | 解説版 → 2.7 | 解説固有の失敗が体系化されていない |
| WebUI 入力支援（統計・たたき台・準備度・チェックリスト） | 解説版 → 2.8 | F8 |
| 意図的な短い表示は最低3フレーム保持（目安） | 共通章に置く | モードに依存しない |

**移植しない（MV 固有）**

| MV 固有の事項 | 持ち込まない理由 |
| --- | --- |
| 完成音源の実測尺が絶対、カット・ループ・音源置換の禁止 | 解説は音声を合成し、尺は内容と発話の実測から決まる。希望尺は目標のまま |
| ビート・BPM・セクションへの同期、`plan/music-analysis.md` | 解説の時間軸は発話。同期対象は「発話と図の変化」 |
| 歌詞を構図要素として設計する、歌詞は提供された内容だけ表示する | 解説の台本はエージェントが書く。画面内テキストは要点であって原文の再現義務は無い |
| 冒頭フックで歌詞を大きく提示 | 解説の導入は「導入の型」軸（2.4）で扱う |
| 全場面で Biim 枠・解説字幕・キャラ自動配置を使わない | 解説は Biim 枠とキャラが標準 |
| 追加 Web 調査の禁止、根拠方針 supplied-only 固定 | 解説は調査が工程の中心。ユーザー設定に従う |
| Aivis・追加 BGM/SE の無効化 | 解説では有効が既定 |
| MV の6軸（配色／タイポグラフィ様式／モーションの言語／構図／質感／テンポ感）をそのまま使うこと | 2.4 の理由により再定義する |
| TuneCore 向け成果物（ジャケット、WAV） | 楽曲配信物であり解説には不要 |

### 2.2 解説版の制作原則「理解先的設計」

- **EX-01（MUST）** `job-template/AGENTS.md` に、MV の「思想先的設計」と同じ階層の節として「理解先的設計（解説動画の制作原則）」を置き、次の7原則を記す。各原則は1〜3文で、判断に使える具体例を1つ以上含む。
  1. **理解ゴールが先、見せ方は後。** 視聴後に視聴者が「言えること・できること」を1〜3文で先に固定する。全場面はその到達に寄与するか、削る。
  2. **説明構造を映像構造へ翻訳する。** 変化の単位を説明の単位（1つの主張、1つのステップ）と揃える（2.3）。
  3. **認知負荷と変化率を区別する。** 1場面で導入する新規概念は原則1つ。発話が新しい概念に触れる瞬間に、画面にも対応する要素を1つだけ加える。動きは視線を導くために使う。
  4. **強調と抑制。** 理解の山場を1〜2箇所決め、その前で情報量を落とす。視聴維持のための演出は理解ゴールに従属させる。
  5. **正確さは演出に優先する。** 根拠のない断定をしない。数値・数式・図は出典と照合する。不確かなことは不確かと言う。装飾のために数値を作らない。
  6. **キャラクターは演者。** 視線・指差し・リアクション・移動で説明に参加させる（現行規則を維持）。
  7. **発話の実測尺が時間軸の正本。** 図の変化・字幕・キャラの動きは実測した発話に合わせる（現行規則を維持）。
- **EX-02（MUST）** この節にも、現行と同じ「品質を上げるための考え方であり、表現手法を禁止・固定するものではない」という位置づけを適用する。ただし原則5（正確さ）と 2.6 のゲートは禁止・固定の例外であることを明記する。

### 2.3 構造翻訳（説明構造 → 映像構造）

- **EX-03（MUST）** `job-template/AGENTS.md` に次の対応表を載せる（文言は調整可、行は削らない）。表の前に「これは出発点であり、内容に合う別の翻訳を選んでよい」と書く。

| 説明構造 | 映像構造への翻訳 |
| --- | --- |
| 因果（AだからB） | 物が物を押す・流れる・連鎖する動き。矢印は結果ではなく過程として描かれる |
| 手順（1→2→3） | 同じ構図の上に積み上げる。前のステップの結果が次の入力として画面に残る |
| 比較対照 | 分割画面・同一尺度・同期した動き。差分だけに色を使う |
| 分類・階層 | ツリーや入れ子の展開。全体と部分の間をズームで往復する |
| 定義 | 対象を隔離し、境界上の例を出し入れして範囲を示す |
| 量・規模 | 実データのチャート。単位と基準物を必ず伴う |
| 時系列・変遷 | 一本の時間軸上をカメラが移動する |
| 論証（主張→根拠→結論） | 主張を画面に留めたまま根拠を積む。反論は対置して見せる |
| 抽象→具体 | 抽象図が具体物へ変形する（またはその逆） |
| 数式 | 項ごとに導入し、変形は項の移動として見せ、各項と図の対応を色で結ぶ |
| 誤解の訂正 | 誤ったモデルを一度動かして見せ、破綻する箇所で壊す |

- **EX-04（MUST）** ストーリーボードの各場面に「構造型」を記録させる（2.5）。全場面が同じ構造型になっている場合は、失敗チェックリストの「スライドの並べ替え」を疑うよう明記する。

### 2.4 方向性の多様性（軸の再定義）

**決定：MV の6軸はそのまま使わず、解説用の6軸に再定義する。** 理由：(1) 解説動画が互いに似るのは見た目より「説明の運び方」が毎回同じだからで、見た目の軸だけでは同質化を防げない。(2) Biim 枠を使う場面は枠・書体・字幕色が標準で固定され、配色・タイポグラフィの自由度が MV より狭い。(3) 解説のテンポは曲ではなく理解負荷に従う。MV の視覚4軸（配色・タイポグラフィ・質感・モーション）は「視覚様式」1軸にまとめて残す。

| 軸 | 決めること | 選択肢の例（WebUI の初期候補。各軸6個以上を用意する） |
| --- | --- | --- |
| 導入の型 | 最初の15秒の入り方 | 素朴な疑問から／よくある誤解を見せて壊す／結論を先に言い切る／具体的な一場面から／数字ひとつの衝撃から／完成図を先に見せて分解する／失敗例から |
| 説明の骨格 | 全体の論理の運び | 因果の連鎖／手順の積み上げ／比較対照／分類と階層／問題→原因→解決／問い→仮説→検証／時系列／全体→部分→全体 |

### 2.6 事前／事後チェック（ゲートと助言の線引き）

**線引きの決定：** ゲートにするのは、**客観的に判定でき、外すと視聴者に実害が出るもの**（誤情報、読めない字幕、切れる音声、未確認のままの納品、記録の欠落）。**主観的な質**（面白さ、演出の巧拙、スロップ感、テンポ）は助言に留め、合否に入れない。これは現行の「表現手法を禁止・固定しない」方針と、ghost 走査の検出件数を助言とする方針（F6）を保つための線である。

**MV の仕組みの読み替え：**
- 歌詞レイヤー QC ゲート（提供された歌詞と表示の整合）→ **台本・根拠・字幕の QC ゲート**（台本と根拠の整合、字幕の収まり、発話との同期）。
- ghost-check → 検出件数は助言のまま。ゲートにするのは「**走査を実施し、孤立フラッシュの全件に照合結果を記録したこと**」。検出したこと自体では不合格にしない（意図した短い表示があり得るため）。

**判定の2系統：**
- **機械判定**：新設するコマンド `npm run qc -- --stage=pre|post`（`runtime/scripts/qc.mjs`）が記録の構造と数値を検査する。
- **レビュー判定**：内容の正しさは機械で判定できないので、**台本を書いたのとは別のコンテキスト**（サブエージェント、別セッション、またはオーナー）が確認し、`reports/qc-review.md` に項目ごとのチェック行で記録する。別コンテキストを用意できない環境では自己レビューを認めるが、`review_mode: self` を記録する（4.3 と同じ縮退規則）。

### 3.2 目指すデザイン言語（決定）

**決定：「Biim 枠 UI」— この道具が出力する映像の標準レイアウト `biim-standard-v1` を、WebUI 自身の骨格・配色・書体にする。**

根拠：
1. **この道具に固有の視覚標準は Biim 枠しかない。** 黒い背景 `#1e1e1e`、灰色の枠線 `#cccccc`、右上の要点・右下の補足・下の字幕という構成、青と赤の白ふち字幕は、すでに製品仕様として定義されている（`src/biim-standard.json`）。UI がそれと同じ言語で作られていれば、ロゴを隠してもこの道具だと分かる。
2. **枠の構成が、そのまま入力道具の情報設計になる。** 主映像＝入力、右上ノート＝要点（ジョブの概要と準備度）、右下ノート＝補足（プレビュー・チェックリスト・検査結果）、字幕＝いまの状態と次の操作。現行の「入力＋右の確認カラム」という構造を変えずに意味を与えられる。
3. **映像の道具として正しい背景になる。** 字幕色や方向性の配色を、実際の映像の地色の上で判断できる。現行の淡緑の地は色の判断を狂わせる。
4. **制作哲学と一致する。** 「何を表現するかが先、手段は後」「作品ごとに一貫したスタイルを定義し、意味のない光沢・ありがちなグラデーションを避ける」という MV の原則を、道具自身が守っている状態になる。

採らなかった案（比較の記録）：動画編集ソフト風のダーク UI（映像制作一般の見た目で、この道具に固有でない）／絵コンテ用紙・進行表の紙面（制作文脈には合うが、出力物との結びつきが無く、紙の模倣が新しい装飾になる）／端末風（Biim とも映像とも関係が無い）。

**デザイン規則（`docs/DESIGN.md` を正本として新設し、ここに書いた規則を移す）**

- **UI-01（MUST）骨格。** 幅1250px 以上では、画面を4領域に分ける：**主領域**（入力フォーム）、**右上ノート**（ジョブの要点：タイトル・モード・尺・出力・資料数・音声と、準備度一覧）、**右下ノート**（切り替え式の補足：レイアウト図・同梱ファイル・JSON・失敗パターン・ゴースト検査結果）、**字幕帯**（画面下に固定：状態の一文、エラーの要約、ZIP 生成ボタン、指示のコピー）。領域の境界は枠線で示す。比率は映像の座標をそのまま写さず、入力作業に適した寸法にする（右カラム320〜420px、字幕帯64〜96px）。
- **UI-02（MUST）セクションの移動手段。** 現行の左サイドバー（ロゴ・ワークスペース表示・ナビ）は廃止し、主領域の上端にセクション番号と日本語名の目次（完了の印つき）を置く。MV では 01〜03 だけを出す現行の挙動を保つ。
- **UI-03（MUST）色。** 使う色は、枠の3色（背景 `#1e1e1e`、枠線 `#cccccc`、文字 `#f4f4f4`）、字幕の2色（青 `#0000ff`、赤 `#ff0000`、どちらも白ふち、または白文字の地色として使う）、彩度0の中間灰（最大5段）に限る。緑系は使わない。それ以外の色が画面に出てよいのは、ユーザーのデータ（字幕色の選択、方向性候補の説明）とレイアウト図だけ。色の値は `:root` の変数で定義し、それ以外の場所に色の直値を書かない。
- **UI-04（MUST）字幕帯の表現。** 解説モードの字幕帯は、状態の一文を**実際の字幕と同じ様式**（フォームで選んだキャラ1の字幕色＋白ふち、字幕書体）で表示し、エラーや不足はキャラ2の字幕色で表示する。字幕色の設定を変えると字幕帯に即時反映される（字幕の見え方の実物プレビューを兼ねる）。MV モードは字幕もキャラも使わないので、字幕帯は白の通常書体で音源の尺と状態を表示する。字幕様式の文字は装飾扱いにせず、同じ内容を通常の文字としても読み上げ可能にする（アクセシビリティ）。
- **UI-05（MUST）形。** 角丸は0。例外は色見本の円と、入力欄の2px まで。影・グラデーション・ぼかし・半透明の重ねは使わない（フォーカス表示の輪郭は可）。枠の境界線は太く（枠SVGと同じ比の太線）、領域内の区切りは1px。
- **UI-06（MUST）文字。** 最小12px、本文14px 以上、本文の行間1.5前後。書体は日本語ゴシックの系統1つ（Noto Sans JP を優先し、無ければ OS の日本語ゴシック）と、数値・パス・コマンド用の等幅1つ、字幕帯専用の字幕書体。外部 CDN からのフォント取得は禁止。同梱フォントを UI で使う場合は初期表示を妨げない読み込みにする（Noto Sans JP は約9.6MB、M PLUS Rounded 1c は約3.6MB）。
- **UI-07（MUST）ラベルと文言。**
  - 英語の飾りラベルを全廃する（3.1 の列挙すべて）。英語を使うのは固有名詞と技術用語（Remotion、Aivis、ZIP、JSON、GLB、fps など）だけ。
  - キャッチコピーと誘導文を全廃する。各欄の説明は「何が・どこに保存され・制作で何に使われるか」を事実として書く（例：「原文のまま brief.md の優先指示に入り、制作原則より優先される」）。
  - 制作者の呼称は「制作エージェント」とし、特定モデル名を固定で書かない。
  - 存在しない機能を示す表示（ワークスペース、パンくず、LIVE）を置かない。
- **UI-08（MUST）アイコン。** 装飾アイコンを廃止し、操作は文字のラベルで示す。記号を使ってよいのは、完了の印、削除・閉じる、展開・折りたたみだけ。「↗」は外部リンク以外で使わない。
- **UI-09（MUST）動き。** UI 自体は動かさない（状態の切り替えは即時、または100ms 以内）。`prefers-reduced-motion` への対応は維持する。
- **UI-10（MUST）名称。** UI・`index.html` の title と説明・README の見出しの表示名を **BiimMotionWebUI** に統一する（公開 repo・Pages の URL と一致させる。U3）。favicon は枠の構成（黒地に灰色の枠線）を図案にする。

### 4.2 階層ワークフロー

| 層 | 担当（標準） | 入力 | 成果物 | してはいけないこと |
| --- | --- | --- | --- | --- |
| L1 PM | Fable 5.2 | オーナーの依頼、repo の実査 | `docs/requirements/<日付>-<名前>.md` | コードを書く、既存ファイルを変える、計画を確定する |
| L2 オーケストレーター | Opus 5.5 高 | 要件定義書 | `PLAN.md`、タスクごとの `DIRECTION.md`、`REVIEW.md`、`ENVIRONMENT.md`、最後に `RETRO.md` | タスクを自分で実装する、自分が書いた実装を合格にする、要件を黙って変える |
| L3 実働 | Opus 5.5 中／Codex 6.1 sol high | `DIRECTION.md` | コード・テスト・文書の変更、`REPORT.md` | `DIRECTION.md` の範囲外を変える、合格を宣言する |
| L4 下請け | 実働のサブエージェント | 実働が切り出した、それだけで完結する小タスク | 実働への返答 | 設計判断、範囲の拡大 |

- **HN-05（MUST）下請けの使い方。** 下請けに向くのは、調査の掃き出し、機械的な置換、テストのひな形、スクリーンショットの撮影など、粗く大量に捌ける単位。複数ファイルにまたがる契約の変更や設計判断は渡さない。**下請けの成果は実働が検品してから `REPORT.md` に載せる。** 下請けの出力がそのままレビューへ行くことはない。
- **HN-06（MUST）ゲート。**

| ゲート | 通過の条件 | 判定者 |
| --- | --- | --- |
| G1 要件 | 要件定義書があり、各要件が判定可能で、未決事項がオーナー判断のものだけ | オーケストレーター（計画できるかを判定）。不足は `QUESTIONS.md` で PM へ差し戻す |
| G2 計画 | `PLAN.md` に、全 MUST 要件 → タスクの対応表、依存関係、各タスクの完了条件と検証方法、環境記録がある | オーケストレーター自身は起案者なので、対応表の抜けを**別コンテキスト**（PM またはレビュー用サブエージェント）が確認する |
| G3 タスク | `REPORT.md` に完了条件ごとの証拠があり、テストとビルドが通る。**レビュー者が検証コマンドを自分で再実行**して確認する | オーケストレーター（実装者と別のコンテキスト） |
| G4 統合 | 全タスクを統合したブランチでテスト・ビルド・MV 非退行・UI の機械基準（UI-C1〜C5）が通る | オーケストレーター |
| G5 オーナー目視 | UI の目視ゲート（UI-A1、UI-A2）と、全体の受け入れ基準（6章） | オーナー。合格後に main へマージ |

- **HN-07（MUST）自己合格の禁止。** 合否を書く者は、その成果を作った者と別のコンテキスト（別エージェントまたは別セッション）であること。レビューは `REPORT.md` の主張を読むだけでなく、差分と実行結果を自分で確かめる。
- **HN-08（MUST）差し戻し。** `REVIEW.md` の判定は「合格／差し戻し／要件差し戻し」の3種。差し戻しには、満たしていない完了条件と期待する状態を具体的に書く。同じタスクの差し戻しが3回に達したら、オーケストレーターはタスクの切り方を見直すか、オーナーへ上げる。要件の不備や矛盾は `QUESTIONS.md` に書いて PM へ戻し、オーケストレーターが要件を書き換えない。
- **HN-09（MUST）受け渡しファイルの様式**（`docs/work/<作業ID>/` 配下。`docs/WORKFLOW.md` に書式例を載せる）。

| ファイル | 書く者 | 必須項目 |
| --- | --- | --- |
| `BRIEF.md` | オーケストレーター（写し） | オーナーの依頼文 |
| `ENVIRONMENT.md` | オーケストレーター | 層ごとの実際の担当（エージェント製品・モデル・effort・セッションの別）、縮退レベル、縮退の理由、自己判定になったゲート |

### 4.3 環境フォールバック

- **HN-10（MUST）最初に環境を判定する。** エージェントは作業の最初に、使えるモデル、サブエージェントの可否、コマンド実行の可否、対話の可否を確かめ、`ENVIRONMENT.md` に記録する。
- **HN-11（MUST）役割の統合順序。** 分業できない場合は**下の層から順に**上へ統合する：(1) 下請けを実働に統合 →(2) 実働をオーケストレーターに統合 →(3) 最後に PM を統合。どこまで統合しても「要件 → 計画 → 実装 → レビュー」の順と、各段階の成果物ファイルは省かない。

| 状況 | 縮退の仕方 |
| --- | --- |
| Fable が使えない | 使える中で最上位のモデルが PM を務める。**オーケストレーターとは別のセッション**で要件定義書を書く |
| モデルが1つしかない | 同じモデルが層ごとに別セッションで順に務める。セッションを分けられない場合は1セッション内で段階を区切り、各段階の成果物ファイルを書き終えてから次へ進む。レビューは差分を読み直し検証コマンドを再実行して行い、`review_mode: self` と記録する |
| サブエージェントが使えない | 下請け層を省き、実働が小タスクを順に処理する。オーケストレーターによる別コンテキストのレビューは維持する |
| Claude Code でも Codex でもないエージェント | `README.md` → `AGENTS.md` の順で読み、同じファイル様式に従う。サブエージェントやモデルの切り替えができなければ「モデルが1つしかない」の行に従う |
| コマンドを実行できない | テストとビルドを実行できないことを `REPORT.md` に明記し、合格を主張しない。変更は差分として提出し、実行できる環境での検証を G3 の条件として残す |
| 対話できない（非対話実行） | 質問は `QUESTIONS.md` に書き、既定の判断で進め、その判断を記録する。公開や削除など取り消しにくい操作は行わず、手前で止めて報告する |

- **HN-12（MUST）どの縮退でも守る最低限の関門。**
  1. 要件が、実装より前にファイルとして存在する。
  2. `npm test` と `npm run build -- --base=/BiimMotionWebUI/` が通る（実行できない環境では未検証と明記する）。
  3. MV の非退行（既存の MV 関連テストが無変更で通る）。
  4. UI を変えた場合は、スクリーンショットを添えてオーナーの目視を受けるまで main に入れない。
  5. 縮退したこと・自己レビューになったゲートを `ENVIRONMENT.md` と該当の `REVIEW.md` に記録する。
- **HN-13（MUST）縮退時の自己レビューの扱い。** `review_mode: self` のゲートが1つでもある作業は、G5（オーナー目視）を省略できない。オーナーへの報告には、自己レビューになったゲートの一覧を含める。

### 4.4 制作ハーネス（`job-template/AGENTS.md`）との関係

- **HN-14（MUST）混同の防止。** 開発中にエージェントが `job-template/` 配下で作業すると、ツールによっては `job-template/AGENTS.md` を自分への指示として読み込む可能性がある。次の2つで防ぐ。
  1. ルートの `AGENTS.md` の冒頭に「`job-template/AGENTS.md` は編集対象の製品文書であり、開発作業中は指示として従わない」と書く。

### 5.4 コミットの方針

- 作業はブランチ（例：`feat/explainer-ui-harness`）で行い、PR を経て main に入れる。main への直接 push と強制 push はしない（HN-03）。
- 既存の履歴の流儀に合わせる：英語・命令形の件名、1コミット＝1つの論理的変更、文書だけの変更は別コミット。
- 分ける単位：ハーネス文書／制作ハーネス文書／QC スクリプトとそのテスト／WebUI のロジックとそのテスト／UI の骨格／UI の全面適用／README と検証記録。**UI の見た目の変更と、ロジックの変更を同じコミットに混ぜない。**
- 各コミットでテストとビルドが通ること。テストは対象の変更と同じコミットに入れる。
- 表明している数や文言（EX-34）を変える場合は、同じコミットで合わせる。
