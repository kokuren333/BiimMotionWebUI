# WORKFLOW — 階層ワークフローの正本

この repo を開発するときの層・ゲート・受け渡しファイル・縮退規則を定める。絶対規則と地図はルートの [AGENTS.md](../AGENTS.md)、Claude Code 固有の事項は [CLAUDE.md](../CLAUDE.md) にある。ここには書き写さない。

## 1. 層と責務

| 層 | 入力 | 成果物 | してはいけないこと |
| --- | --- | --- | --- |
| L1 PM | オーナーの依頼、repo の実査 | `docs/requirements/<日付>-<名前>.md` | コードを書く、既存ファイルを変える、計画を確定する |
| L2 オーケストレーター | 要件定義書 | `PLAN.md`、タスクごとの `DIRECTION.md`、`REVIEW.md`、`ENVIRONMENT.md`、最後に `RETRO.md` | タスクを自分で実装する、自分が書いた成果物を合格にする、要件を黙って変える |
| L3 実働 | `DIRECTION.md` | コード・テスト・文書の変更、`REPORT.md` | `DIRECTION.md` の範囲外を変える、合格を宣言する |
| L4 下請け | 実働が切り出した、それだけで完結する小タスク | 実働への返答 | 設計判断、範囲の拡大 |

- **下請けの使い方。** 下請けに向くのは、調査の掃き出し、機械的な置換、テストのひな形、スクリーンショットの撮影など、粗く大量に捌ける単位。複数ファイルにまたがる契約の変更や設計判断は渡さない。下請けの成果は実働が検品してから `REPORT.md` に載せる。下請けの出力がそのままレビューへ行くことはない。
- **自己合格の禁止の運用**（規則はルート `AGENTS.md` 絶対規則8）。レビュー者は `REPORT.md` の主張を読むだけで判定せず、差分を自分で読む。L2 が書いた `DIRECTION.md`・`RETRO.md` も、PM またはレビュー用サブエージェントなど別コンテキストが確認する（計画は G2）。
- **交差レビュー。** 危険度の高いタスク（全員が依存する契約、ゲートの実装、MV と共有するコード、機能を落とす危険のある UI 変更）は、L2 の判定に加えて、実装者と別のエージェント製品が差分を読み、`REVIEW.md` に併記する。

## 2. ゲート

| ゲート | 時点 | 通過の条件 | 判定者 |
| --- | --- | --- | --- |
| G1 要件 | 計画の前 | 要件定義書があり、各要件が判定可能で、未決事項がオーナー判断のものだけ | L2（計画できるかを判定）。不足は `QUESTIONS.md` で PM へ差し戻す |
| G2 計画 | 発注の前 | `PLAN.md` に、全 MUST 要件 → タスクの対応表、依存関係、各タスクの完了条件と検証コマンド、環境記録がある | L2 は起案者なので、別コンテキスト（PM またはレビュー用サブエージェント）が対応表の抜けを確認する |
| G3 タスク | 各タスクの `REPORT.md` 提出後 | `REPORT.md` に完了条件ごとの証拠がある。レビュー者が検証コマンドを自分で再実行して合格。MV 非退行。`DIRECTION.md` の範囲外の変更が無い | L2（実装者と別のコンテキスト）。交差レビュー対象は他製品の実働も |
| G4 統合 | PR ごと | 統合ブランチで次がすべて合格：`npm test`、`npm run build -- --base=/BiimMotionWebUI/`、`npm run qc`（対象がある場合）、MV 非退行、`PLAN.md` が定める統合検査、実装者以外のレビュー。UI を変えた PR は、スクリーンショットを取得して `VERIFICATION.md` に記録済みであること | L2 が統合ブランチで再実行する。L2 自身の成果物を含む PR は別コンテキストが判定する |
| 公開（ゲートではない） | G4 合格の直後 | PR を main へマージする（論理コミットを残すためマージコミット）。Pages が自動でデプロイされる | L2 |
| 公開後確認（ゲートではない） | デプロイ完了後 | CI（テスト・ビルド・デプロイ）が成功。公開 URL でスクリーンショットを撮り直し、公開前の記録と一致することを `VERIFICATION.md` に追記 | L2（記録のみ） |

- スクリーンショットは**証拠記録**であり、誰かの判定を待つ点ではない。オーナーの感想・指摘は公開後の任意フィードバックとして `docs/work/<作業ID>/FEEDBACK.md` に記録し、必要なら修正タスクにして同じゲートを通す。
- **公開後に問題が見つかった場合。** 表示が壊れている・機能が落ちている場合は、L2 が `git revert -m 1 <マージコミット>` の PR を作り、`npm test` とビルドが通れば即マージしてよい（緊急時の例外。巻き戻しは新しいコミットで行い、履歴は書き換えない）。例外を使ったら、次の G3 で別コンテキストが巻き戻しの差分を事後確認して記録する。原因は修正タスクとして再発注する。見た目の好みに関する指摘は巻き戻さず、修正タスクにする。
- **差し戻し。** `REVIEW.md` の判定は「合格／差し戻し／要件差し戻し」の3種。差し戻しには、満たしていない完了条件と期待する状態を具体的に書く。同じタスクの差し戻しが3回に達したら、L2 はタスクの切り方を見直すか、オーナーへ上げる。要件の不備や矛盾は `QUESTIONS.md` に書いて PM へ戻し、L2 は要件を書き換えない。

### ブランチとコミット

- 作業ごとに波のブランチ（例：`feat/<名前>`）を main から作り、実働はタスク用ブランチ（例：`task/<タスクID>-<名前>`）を波のブランチから切る。G3 合格後に L2 が波のブランチへ取り込む。
- 件名は英語・命令形。1コミット＝1つの論理的変更。文書だけの変更は別コミット。テストは対象の変更と同じコミットに入れる。UI の見た目の変更とロジックの変更を同じコミットに混ぜない。
- エージェント環境が定める帰属行はコミットメッセージと PR 本文にだけ書き、ファイルには書かない。
- 差分の検証には基準コミットを付ける（`git diff <BASE>...HEAD`）。基準の無い `git diff` はコミット後に再現できない。

## 3. 受け渡しファイル

置き場所は `docs/work/<作業ID>/`（作業 ID は `<日付>-<名前>`）。タスクごとのファイルは `tasks/<タスクID>/` に置く。ローカルの下書き・起動スクリプト・ログは `.agent-work/` に置き、残すべき記録だけをここへ移す。

| ファイル | 書く者 | 必須項目 |
| --- | --- | --- |
| `BRIEF.md` | L2（写し） | オーナーの依頼文（ローカル情報を除く） |
| `ENVIRONMENT.md` | L2 | 層ごとの実際の担当（エージェント製品・モデル・effort・セッションの別）、縮退レベル、縮退の理由、自己判定になったゲート |
| `PLAN.md` | L2 | タスク一覧、依存関係、要件 → タスクの対応表、ゲートの予定、コミット方針 |
| `tasks/<タスクID>/DIRECTION.md` | L2 | 目的、対応する要件 ID、触ってよい範囲と触らない範囲、完了条件（判定可能な形）、検証コマンド、依存、禁止事項、基準コミット |
| `tasks/<タスクID>/REPORT.md` | L3 | 起動時チェックの結果、変更したファイル、実行したコマンドと結果、完了条件ごとの証拠、指示からの逸脱と理由、未解決の点、下請けに出した範囲 |
| `tasks/<タスクID>/REVIEW.md` | レビュー者 | 判定、完了条件ごとの確認結果（再実行したコマンド）、差し戻し項目、レビュー者と `review_mode` |
| `QUESTIONS.md` | 誰でも | 質問、宛先（PM・オーナー）、回答が無い間の既定、回答、決定日 |
| `FEEDBACK.md` | L2 | 公開後に受けた指摘、対応したタスク |
| `RETRO.md` | L2 | 機能した点・しなかった点、このファイルへの反映内容 |

`RETRO.md` の学びは、作業を閉じる前にこのファイルへ反映する。

### 書式例

`DIRECTION.md`

```markdown
# DIRECTION — T4 QC 実装
- 作業ID: `2026-11-13-explainer-ui-harness` / 層: L3 実働 / 基準コミット `<BASE>`: `abc1234`
- 目的: 解説ジョブの事前・事後 QC を `npm run qc` で機械判定する
- 対応要件: EX-14〜EX-19
- 触ってよい範囲: `job-template/runtime/scripts/qc.mjs`、`tests/qc.test.ts`
- 触らない範囲: `src/`、`tests/job.test.ts` の既存行、`job-template/AGENTS.md`
- 完了条件:
  - [ ] 根拠の無い主張で `verdict: fail`、全条件を満たすと `pass`（テストで表明）
  - [ ] `npm test` と `npm run build -- --base=/BiimMotionWebUI/` が合格
- 検証コマンド: `npm test`、`git diff --check <BASE>...HEAD`
- 依存: T1 / 禁止事項: 承認を求められたら承認せずに止めて REPORT に書く
```

`REPORT.md`

```markdown
# REPORT — T4 QC 実装
- 実働: Codex（モデル・effort）/ 縮退レベル: 1（サブエージェント不可）/ 自己判定になるゲート: なし
- 変更したファイル: `job-template/runtime/scripts/qc.mjs`（新設）、`tests/qc.test.ts`（新設）
## 完了条件ごとの証拠
| 条件 | 証拠 |
| --- | --- |
| 不合格事例 | `npm test` の出力: `✔ qc fails on claims without sources` |
| テスト・ビルド | `ℹ pass 41 / fail 0`、`vite build` 成功 |
## 逸脱と理由 / 未解決 / 下請けに出した範囲
- なし / 字幕係数は実測待ち / テストのひな形のみ（検品済み）
```

`REVIEW.md`

```markdown
# REVIEW — T4 QC 実装
- 判定: 差し戻し / レビュー者: L2（実装者と別セッション）/ review_mode: independent
| 条件 | 再実行したコマンド | 結果 |
| --- | --- | --- |
| テスト | `npm test` | 合格 |
| 範囲 | `git diff --stat <BASE>...HEAD` | `src/job.ts` に範囲外の変更 |
## 差し戻し項目
1. `src/job.ts` の変更を外すこと（期待：差分が DIRECTION の範囲内だけ）
```

`ENVIRONMENT.md` の起動記録（1セッション1行）

```markdown
| 日時 | タスク | 層 | 製品／モデル／effort | サブエージェント | コマンド実行 | 対話 | ネットワーク | 縮退レベル | 備考 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 2026-11-13 | T4 | L3 | Codex／（モデル）／high | 不可 | 可 | 不可 | 可 | 1 | — |
```

`QUESTIONS.md`

```markdown
| ID | 宛先 | 質問 | 既定（回答が無い間） | 回答 | 決定日 |
| --- | --- | --- | --- | --- | --- |
| Q7 | PM | EX-17 の係数を実測値で置き換えてよいか | 実測値を使い VERIFICATION.md に記録 | | |
```

## 4. 起動時チェック

各セッションは最初に次を確かめ、L2 は `ENVIRONMENT.md` に、L3 は `REPORT.md` に記録する（L2 が後で `ENVIRONMENT.md` へ転記する）。

1. 自分の層（ルート `AGENTS.md` §2）。
2. エージェント製品とモデル・effort／サブエージェントを起動できるか／コマンドを実行できるか（`node -v`、`npm test`）／対話できるか／ネットワーク（`npm ci`、Pages の閲覧）／タスクが必要とする外部環境（ヘッドレス Chrome、Aivis エンジン、GPU レンダーなど）。
3. 次節の縮退レベルを決め、「レベル・理由・自己判定になるゲート」を書いてから作業に入る。

## 5. 環境と縮退

分業できない場合は**下の層から順に**上へ統合する：(1) 下請けを実働に統合 →(2) 実働をオーケストレーターに統合 →(3) 最後に PM を統合。どこまで統合しても「要件 → 計画 → 実装 → レビュー」の順と、各段階の成果物ファイルは省かない。

| レベル | 状況 | 運用 | 自己判定になるゲート |
| --- | --- | --- | --- |
| 0 | 標準（PM・L2・実働が別セッション、サブエージェントあり） | このファイルどおり | なし |
| 1 | サブエージェントが使えない | L4 を省き、実働が小タスクを順に処理する。L2 による別コンテキストのレビューは維持 | なし |
| 2 | 実働のエージェント製品が1つしか無い | すべての L3 を残った製品が担当。交差レビューは別セッションの同一製品に置き換える | なし（別セッションなら independent） |
| 3 | モデルが1つだけ・セッションは分けられる | 同じモデルが層ごとに別セッションで順に務める | なし（別セッションなら independent） |
| 4 | セッションも分けられない（1セッションで全層） | 段階を区切り、各段階の成果物ファイルを書き終えてから次へ。レビューは差分を読み直し検証コマンドを再実行して行う | G2・G3・G4 すべて `review_mode: self` |
| 5 | コマンドを実行できない | テストとビルドを実行できないことを `REPORT.md` に明記し、合格を主張しない。変更は差分として提出し、実行できる環境での検証を G3 の条件として残す。検証されるまでマージしない | 実行を要するゲートは「未検証」 |
| — | PM に充てる上位モデルが使えない | 使える中で最上位のモデルが、L2 と別のセッションで PM を務める | — |
| — | 対話できない（非対話実行） | 質問は `QUESTIONS.md` に書き、既定の判断で進め、その判断を記録する。承認を求められたら承認せずに止め、状態を記録する。取り消しにくい操作の扱いはルート `AGENTS.md` 絶対規則9 | — |

**どの縮退でも守る最低限の関門。** ルート `AGENTS.md` の絶対規則（特に 1・3・4・8）に加えて：

1. UI を変えた場合は、スクリーンショットを取得して `VERIFICATION.md` に記録するまで main に入れない。
2. 縮退したこと・自己レビューになったゲートを `ENVIRONMENT.md` と該当の `REVIEW.md` に記録する。

**自己レビューの扱い。** `review_mode: self` のゲートがあっても作業は止めず、上の記録をして進める。オーナー目視の強制には使わない。公開後の報告には、自己レビューになったゲートの一覧を含める。

### エージェント製品ごとの注意

- **Claude Code**：[CLAUDE.md](../CLAUDE.md) を参照。
- **Codex**：専用ファイルは無く、ルートの `AGENTS.md` を直接読む。
  - Codex は作業ディレクトリまでの各階層の `AGENTS.md` を連結して読む。`job-template/` 配下で作業すると `job-template/AGENTS.md` も指示として入るが、開発中はルート `AGENTS.md` §1 に従い、制作指示としては扱わない。
  - 標準の割り当ては L3 実働（Codex 6.1 sol、effort high）。コード・検証系のタスクを受け持ち、文書・UI 系の実働（Claude Code）と交差レビューを組む。
  - サンドボックスや承認設定によってネットワークやファイル書き込みが制限される。`npm ci` が通らずテストを実行できなければレベル5として記録する。`codex exec` などの非対話実行は §5 の「対話できない」行に従う。
  - サブエージェントを使えない設定ならレベル1として記録する。
- **その他のエージェント**：`README.md` → ルート `AGENTS.md` → このファイルの順に読み、同じファイル様式に従う。モデルやセッションを切り替えられなければレベル3または4に従う。
- **Windows**：検証コマンドは POSIX シェル（Git Bash など）で実行する前提で書かれている。PowerShell では `grep`・`wc` などが無いか挙動が違うので、同等のコマンドに置き換えたら `REPORT.md` にその旨を書く。
