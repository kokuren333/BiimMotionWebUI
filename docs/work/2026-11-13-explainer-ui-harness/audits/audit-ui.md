# BiimMotionWebUI UI監査 — スロップ要素・維持機能・刷新制約

- 監査日: 2026-11-13
- 対象: `repo-audit/`（GitHub Pages 公開中の BiimMaker — Motion Job Studio、読み取り専用クローン）
  - `src/App.tsx` — 2,164行 / 85,607字（約91KB、単一ファイル）
  - `src/style.css` — 2,025行 / 約34KB（単一ファイル、CSS Modules / プリプロセッサなし）
  - `index.html` — 23行
- 方法: ソース実測（色・サイズ・角丸の出現頻度集計、コンポーネント/状態の全数走査）。ブラウザでの実描画確認はしていないため、ピクセル単位の見え方は CSS 値からの推定である。
- 結論を一言で: 機能は本物（後述の維持リスト参照）だが、見た目は「緑がかったオフホワイト＋白カード＋小さな英語眉見出し」という、AI生成SaaSテンプレートの最も無難な組み合わせで統一されており、**Biim／kokuren の固有性がブランド名と文言以外に一切出ていない**。色もタイポも部品も「どこかで見た」ものだけでできているのがスロップ感の正体である。

## (1) スロップ要素リスト（要素 → なぜそう見えるか）

### A. 配色

| # | 要素（所在） | なぜスロップに見えるか |
|---|---|---|

### F. コピー（文言）の調子

| # | 要素 | なぜスロップに見えるか |
|---|---|---|
| F1 | ヒーロー: 「伝えたいことを、動きのある動画へ。」＋「企画と資料をまとめて、映像制作の準備を。構成も、演出も、実装も。あとはOpusへ。」／フッター標語 `IDEAS DESERVE MOTION.`／dialog「動画制作のための、小さな出発点。」 | 意味は正しいが、AIコピーの定型（体言止めの断片文＋英語標語＋「小さな〜」）で、kokuren の文体（思想先的設計、具体的な制作用語）とは無縁。誰の製品か分からない |

## (2) 維持すべき機能リスト（刷新で落としてはいけないもの）

App.tsx 実装済み・実測確認。★はこの製品の差別化機能で、刷新後も同等以上の目立ち方を保証すること。

### 基盤・モード
1. **5セクション構成**（01 動画の企画 / 02 参考資料と指示 / 03 デザイン方向性 / 04 キャラクター / 05 音声と出力）＋「演出と調査の詳細」アコーディオン（解説のみ）。サイドバーナビはスクロール連動（IntersectionObserver）で現在地表示＋セクション完了チェック（`completed[5]`）を持つ。
2. ★**MV／解説モード切替**（Section 01 の制作モード）。切替時に**モード別ドラフトを保持**（`modeDrafts` / `modeSettingsFor` / `switchVideoMode`）し、04・05・詳細設定は MV で非表示、ナビも3セクションに追随する。
3. **サンプル入力**（「30秒のサンプルを入力」: 解説の完成例を一括投入、モードドラフトはリセット）。

### Section 01（企画）
4. タイトル／目的（MVでは「MVで表現したいこと」にラベル変化）／対象視聴者／希望尺（秒、単位付き入力）。必須3項目。
5. ★MV専用: 曲の雰囲気・世界観、**歌詞入力＋歌詞統計**（行数・ブロック数・セクション見出し数・最長行文字数、20字超行への警告表示、`lyricStats`）、差別化メモ（03側にも連携）。
6. ★MV専用: **完成音源ファイル選択＋尺の自動実測**（`Audio` メタデータ、0〜7,200秒の検証、状態文の表示、実測尺を希望尺より優先）。

### Section 02（資料）
7. 参考URL（複数行テキスト）、**資料ドロップゾーン**（ドラッグ＆ドロップ＋ファイルボタン、dragging 状態）、添付一覧（種別アイコン・名前・サイズ・削除）、添付件数表示、動画全体への指示テキスト。

### Section 03（方向性）
8. デザイン方向性テキスト、レイアウト切替（全画面／Biim枠、`usesFullScreen`）、現在値のタグ表示（レイアウト／Motion graphics／Lyric typography or 3D character）。
9. ★MV専用「**方向性のたたき台**」: 6軸の組み合わせによる候補3案カード（`directionCandidates`）、「別の組み合わせ」引き直し（seed更新）、候補のデザイン欄への追記（追記済み表示）、「変化の軸と考え方」details、差別化メモ欄。
10. 素材の生成オプション（両モード共通）: 画像生成（imagegen）許可／動画生成AI許可のチェックと注記。

### Section 04・05＋詳細（解説専用）
11. キャラクター: 1人／2人切替（2人目入力は保持）、各人の名前・読み・性格・口調・役割・備考・基本配置（左/右）、**字幕色（カラーピッカー＋HEX入力＋白ふちサンプル表示）**、話者スタイル（styleId）・話速・読み方指示、GLBファイル選択。
12. 音声と出力: 音声エンジン選択、話者別設定、BGMファイル選択、BGM・SE制作方針、向き（横16:9／縦9:16）、解像度、fps（24/25/30/60）。
13. 詳細設定: テンポ／派手さ／モーション量／Biim使用率／キャラ登場頻度、数式・図解・チャート方針、Web調査許可、根拠資料の扱い。

### 右カラム（プレビュー／書き出し／引き継ぎ）
14. ★**プレビューカード**: タブ3種（レイアウト概形／ファイル構成ツリー／project JSON）。概形は Biim枠・全画面・縦型・1人/2人・キャラ配置・字幕バーを入力連動で描画し、ジョブ名と仕様一覧（尺・出力・資料・音声ほか `job-specs`）をライブ表示。
15. ★**書き出しカード**: 入力バリデーション結果に基づく ready 状態、添付合計サイズ、ZIPダウンロードボタン、生成中 progress、成功メッセージ。MV時は **readiness リスト**（必須/推奨/任意の6項目チェック＋実測値表示）。
16. **入力バリデーション表示**: `validateForm` の全問題を一覧表示し、送信時にエラーへスクロール＋フォーカス（`role=alert` 相当の領域）。※方式の改善は可だが「全問題を列挙して直せる」ことは維持。
17. **ハンドオフカード**: モード別エージェント指示文（`agentPromptFor`）の表示＋クリップボードコピー（成否ステータス）、runtime タグ表示。MV時は品質チェックリスト（previewで確認する失敗パターン、details）。

## (3) 刷新の技術的制約

### 構造・コスト
1. **App.tsx が単一 2,164行・約91KB の単一コンポーネント**（`App` 1個＋`Icon`＋`Section`＋`AttachmentList` のみ）。状態は約20個の `useState/useRef` が同居し、JSX・状態・副作用（音源実測、IntersectionObserver、ZIP生成、クリップボード、ghost-check読込）が分離されていない。見た目だけ差し替える場合でも、クラス名の付け替えが全域に及ぶ。**刷新は「CSS貼り替え」で済む範囲と、コンポーネント分割（セクション単位・右カラム単位）を伴う範囲を先に切り分けること。**分割するなら `job.ts`（約42KB、型・検証・ZIP生成）との境界は既存のまま使える（UIは `MotionForm/JobAssets` 経由でのみ接続）。
2. **style.css も単一 2,025行・約34KB**、クラス名は BEM 風でも体系風でもない素の名前（`.form-section` 等）で App.tsx と 1:1 に密結合。末尾に上書きパッチ（schematic の黒系再定義、MV支援クラス、ghost-check viewer）が追記された構造のため、**部分編集はカスケード事故の温床**。刷新時は CSS の全面書き換え（またはトークン化した上での再生成）を前提に見積もること。既存クラスの温存は必須ではないが、その場合は App.tsx 側の className 全量付け替えとセットになる。
3. 依存は React 19 + jszip のみ（package.json）。**アイコンライブラリ、UIライブラリ、フォント、画像アセットは一切なし**（favicon は index.html 内の data URI SVG）。刷新でフォント読み込み・アイコンセット・画像を使う場合は新規導入が前提で、GitHub Pages の静的配信（`vite build --base=/BiimMotionWebUI/`）で完結する形に限る。バックエンド・APIキーなしという製品制約は UI 刷新でも維持（README 明記）。

### 壊してはいけない接続点
4. セクションの `id`（`concept/sources/direction/character/voice`）は IntersectionObserver の現在地判定とサイドバーのアンカー遷移の両方に使われている。ID変更はナビ機能の破壊とセット。
5. プレビュータブは `role=tab/tabpanel` と `aria-selected`、詳細設定は `aria-expanded/aria-controls`＋`hidden` 切替、エラー領域は送信時の `scrollIntoView+focus` と結びついている。見た目の再設計でもこの a11y 配線は引き継ぐこと。
6. ファイル入力は「透明な `<input type=file>` を `.file-button` ラベルで覆う」実装が3系統（資料/GLB・音源・BGM/ghost-check）ある。部品デザインを変える場合は覆い構造とフォーカス表示（`:focus-within`）を壊さないこと。
7. MV／解説でフィールドの表示・必須条件・ZIP内容物が変わる条件分岐（`isMV` が約30箇所）が JSX 全体に分布している。レイアウト再構成時に分岐を取りこぼすと「MVで04/05が出る」「解説で歌詞統計が出ない」等の機能退行が起きる。(2) のリストを回帰チェック表として使うこと。
8. レスポンシブは既存5ブレークポイント（1600/1250/1080/920/650px）で、920px 以下では右カラムが上部へ回り、650px 以下ではプレビューカードが非表示になる現行仕様がある。刷新でこの挙動を変える場合は意図的な仕様変更として扱う（無言で変えると「モバイルでプレビューが消えた/出た」が事故になる）。

### デザイン刷新側の制約（監査からの要請）
9. 色は現行の場当たり154色を捨て、**トークン（変数）化した上で色数を大幅に制限**すること。ただし状態色（成功/警告/エラー/ready）は意味色として体系化し、現行の淡すぎる色差（判別不能な readiness/status-dot）は解消すること。
10. 本文の最小サイズは現行の 7〜9px 常用を改めること（特に ghost-check 結果、handoff、export-note、job-specs）。英語眉見出しを残す場合も、装飾ではなく情報として必要な箇所に限定すること。
11. フォントは「宣言だけ Inter」を解消すること（実際に読み込むか、宣言を実フォントに合わせるか）。和文見出しと欧文の混植方針（ウェイト・字間）を1つに定めること。
12. アイコンは SVG 体系に統一し、`♫`・`↗`・`+/−` の文字グリフ流用をなくすこと。ブランドマーク（再生三角＋角丸正方形）も刷新対象に含めること。
13. バリデーション表示は、刷新後も「全問題の列挙＋該当箇所へ辿れる」導線を維持した上で、可能ならフィールド単位表示へ格上げすること（現行方式の単純な見た目変更だけで済ませない）。
14. プレビュー概形（schematic）は入力連動の描画ロジック（Biim/全画面/縦型/人数/字幕位置）が CSS クラス切替で実装されている（`.full-screen/.portrait/.duo`、`transform: scale()` でのキャラ配置等）。見た目を変える場合はこの切替仕様と字幕色設定の連動を再現・検証すること。CSS末尾の黒系上書きパッチは刷新時に必ず整理（重複定義の解消）すること。
